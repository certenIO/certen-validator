# RB12-SEPOLIA-SPINE: a resumable execution-header spine for eth-sepolia/finalized/v1 (live defect F6)

Base: origin/main 0e10cb92, merged with origin/pv2/rb12-train2 (986b195a). Builder side only. Nothing a verifier reads changes.

## The defect

Eleven Sepolia (11155111) `finalized` legs sit at `finality_build_timeout{after=300s}` (live, read-only, 2026-10-23 19:25Z: 11 status rows, `attempt` 6, next ask about three hours out). `ethsepolia.Prover.assemble` fetched the whole execution-header spine (4638 headers, 3.1 MB for the day-old recorded leg) in one call and, when the build's 300 s ended, threw away everything it had fetched, so every attempt began at the leg block again and none could finish.

## What changes

1. **Chunks, walked from the finalized head down** (`pkg/finality/ethsepolia/spine.go`). The head's hash comes from the light client; every header names its parent by hash, so each chunk is authenticated, when it is fetched, against the hash the chunk above it commits to (`checkSpan`). A header a provider invents cannot enter a kept chunk (`TestHeadersThatDoNotChainToTheFinalizedHeadAreNeverKeptAndTheNextAttemptRecovers`: six kinds of bad answer, none kept, the next attempt completes).
2. **Kept in the insert-only capture store and in the process.** A complete aligned window of `SpineWindow` = 40 headers is one `proof_finality_capture` row: chain 11155111, `l1_block` = the window's last block, `l1_hash` = that header's hash, item `spine/n<count>`, bytes = the RLP list of the headers. The key commits to every byte, so the same chunk is the same row for every leg and every validator; identical duplicates are accepted and other bytes under a key are the named `finality_spine_row_invalid{reason=row_conflict}` (`TestAnIdenticalRowWrittenByAnotherValidatorIsAcceptedAndADifferentOneIsNamed`). The window that ends at the head's parent moves with the head and is never kept; the lowest window is cut at the leg block (nothing below the leg is ever requested, so recorded replays are unchanged). A bounded process cache (24 MiB) holds the same chunks, and a lock per chunk makes legs that want the same chunk at once fetch it once (`TestLegsAskingForTheSameChunkAtOnceFetchItOnce`, gated interleaving, not a race loop).
3. **Resume at the first chunk not kept; the budget counts new work only.** An attempt spends at most `AttemptBudget` (default 150 s, never more than what is left of the build's deadline minus `AttemptReserve`, a fifth of it and at least 10 s) on fetching; reading kept chunks costs nothing, WAITING for another leg's fetch of the same chunk counts (review defect D1: before, n legs behind one provider ran n times the budget and ended at the build's deadline). A new fetch also needs the deadline to still have the reserve and a fetch as long as the longest so far (`FetchFits`), the wait is bounded by what is left of the budget, and one provider call by that plus half the reserve (`TestConcurrentLegsEachEndInTheProgressStateAtTheirBudgetNotAtTheBuildsDeadline`: real goroutines, real deadline, 4 legs and 11 legs). `BudgetAllows` is exact at the boundary (`TestTheAttemptBudgetCountsNewWorkOnlyAndIsExactAtTheBoundary`: the budget that admits three fetches completes with three calls, one nanosecond less stops at two and the state says how far it got). `TestANewProcessResumesFromTheKeptRowsAtTheFirstMissingChunk`: a new process asks for the top, reads the kept rows, and its next request is the first missing chunk.
4. **A named progress state instead of a timeout.** `finality_pending{reason=awaiting_spine, have, need, next_attempt_at}` (`have` = spine headers obtained and authenticated from the head down, `need` = the whole spine, `cause` when a provider or the store stopped it, redacted by `ethrpc.RedactText`; `TestAProviderErrorTextIsRedactedInTheProgressState`). Registered in `testdata/finality/states.json` (pending reason `awaiting_spine`, field `cause` of `finality_pending`, state `finality_spine_row_invalid` with a closed reason set); `TestTheRegistryRecordsTheNewPendingReasonAndTheNewOperationalState` and `TestTheStatesTheSpineWalkRaisesConformToTheRegistry`. The next ask is the pause: 2 s after a spent budget, the provider's own Retry-After after a throttle that stated one (a bare 429 reports none and escalates like any failure: review defect D3, `TestABare429FromTheRealSourceEscalatesTheNextAttemptLikeAnyFailure`), 30 s doubling to 15 min after attempts that kept no new chunk (`PauseAfter`, pinned in `TestPauseAfterByKindAndStalls`; fetching only the top window, which is never kept, is no progress: `TestAnAttemptThatFetchedOnlyTheUnkeptTopMadeNoProgress`). `finality_spine_row_invalid` is `ClassFailure` in the retry table (see Findings).

**A kept row that is not what its key says is a miss, never a stop** (review defect D2). The table is insert-only, so such a row can never be corrected; stopping at it would block every leg whose spine contains the window for ever. The chunk is fetched from the provider, authenticated by the same hash chain, used and kept in the process only, nothing is written over the row, and the row is reported by name (`finality_spine_row_invalid{reason}` in the log and `certen_finality_spine_rows_invalid_total{reason}`). The same holds for a Put that finds other bytes under the key. `TestABadKeptRowIsAMissThatIsReportedAndNeverBlocksALeg` (three fresh processes, a healthy provider), `TestAPutConflictWithAStoredRowIsReportedAndTheAuthenticatedChunkIsUsed`, `TestEveryKindOfWrongKeptRowIsReportedByNameAndReplacedFromTheProvider`. Each process that meets such a row fetches that window again; nothing is trusted from the row.

**Metrics and the alert** (`pkg/metrics/finality_spine_metrics.go`, `pr/rb11-alerts.md`): `certen_finality_spine_headers_total{outcome=fetched|reused}`, `certen_finality_spine_attempts_total{outcome=complete|budget|throttled|error|failed}`, `certen_finality_spine_rows_invalid_total{reason}`, `certen_finality_spine_legs_awaiting` and `certen_finality_spine_stalled_attempts_max`. Alert: `certen_finality_spine_stalled_attempts_max >= 3` for 30 min. A leg is progressing when the headers of kept spans it has in hand grow from one attempt to the next, whoever fetched them (a leg that follows another and only reuses the chunks that one kept gains headers, V-SPINE-2 N1: `TestALegThatOnlyReusesTheChunksOfAnotherLegIsProgressingNotStalled`), and the same definition drives the pause back-off; the two gauges are read at every scrape and forget a leg not attempted for an hour (a leg another validator completed is never attempted here again: `TestAStalledLegIsForgottenAfterAnHourWithoutAnAttempt`). `TestSpineMetricsAreNonZeroWhenALegStallsAndZeroWhenItCompletes` scrapes the registry: the gauge is 1, 2, 3 after three attempts without a new kept chunk and the leg is counted as awaiting; both are 0 when the spine completes.
5. **Provider pacing and Retry-After** (`pace.go`, `execsource.go`). A 429 with a Retry-After the call cannot afford (longer than 30 s, or not inside the caller's deadline) ends the call at once and hands the provider's own Retry-After to the caller (`SourceError.Throttle`; zero when the provider stated none); one that fits is waited out, never shortened (`ThrottleWait`, exact boundaries in `TestThrottleWaitHonoursAStatedRetryAfterAndGivesUpExactlyWhereTheWaitCannotBeAfforded`). The gap between requests (all legs together, floor 100 ms from the wiring, `TestRTSepoliaProverIsWiredWithTheCaptureStoreTheLoggerAndARequestGap`) rises on 429 and falls on success (`NextGap`). Error text goes through `RedactText` as before.
6. **Correctness unchanged.** `Kind.Verify` judges the assembled evidence exactly as before. The three recorded legs build byte-identical to their recorded evidence and verify (`TestRecordedLegsBuildByteIdenticalThroughTheKeptSpineAndVerify`); the day-old leg completes in exactly the planned number of attempts with the right progress between (`TestADayOldLegCompletesInThePlannedNumberOfAttemptsWithTheProgressStateBetween`); a corrupted kept chunk is replaced from the provider and the evidence is still the recorded evidence, and the same substitution put into evidence by hand is refused by the verifier as `finality_header_chain_broken` (`TestACorruptedKeptChunkIsReplacedAndTheVerifierRefusesTheSameCorruption`).

## What happens to the 11 live legs on the first tick after the deploy

The upgrader's schedules (`next`, `fails`) are in memory (`upgrader.go`), so a restart makes all 11 due on the first pass, none a suspect. Each answers `awaiting_spine{have, need}`, replacing its `finality_build_timeout` row; they share the chunks (aligned windows are shared between legs), and every attempt starts at the first chunk the store lacks. `TestElevenLegsOfOneFinalityUpdateDrainOnTheFirstTicksAndShareTheirChunks`: eleven legs of the recorded update at eleven depths, empty store, 0.5 s a header: never an error, all eleven verify, drained in 6 rounds, 4637 distinct headers fetched in 127 calls (the only headers fetched twice are at leg boundaries, fewer than one window per leg). After the deploy `pr/rb11-prod-shape-check.sh` checks SP1/SP2 (below).

## Memory (p0-live budget)

Measured with a tight GC target on the recorded day-old leg (spine 3,128,792 bytes, 4638 headers), whole `BuildLeg` including light-client links, container and verification: one-piece build at the base 10.8 to 11.8 MB peak heap growth (3 runs); after the change 11.2 to 11.7 MB with a fresh prover and 13.2 to 14.6 MB with the process cache holding the spine. The build's hold reserves 4,693,683 bytes (1.5 times the spine; `TestADayOldLegsBuildStaysWithinTheMemoryBudgetItReserves`), and an over-budget build is `finality_memory_budget_exceeded` with nothing built (`TestTheSpineIsHeldWithinTheBuildsMemoryReservationAndAnOverBudgetBuildIsNamed`). The largest spine the verifier accepts (16384 synthetic headers, 10.8 MB) peaks at 25 to 27 MB including an in-memory copy of the store (`TestPeakHeapOfTheLargestSpineStaysWithinAFewTimesItsSize`). The process cache is bounded at 24 MiB.

## Production shape

- Real Sepolia headers: the tests use the recorded finality_eth_sepolia2 legs (23-item headers, averaging 645 to 674 bytes).
- Real table: `pkg/database/finality_spine_test.go` builds the recorded gloas_period leg through `proof_finality_capture` on PostgreSQL with a new prover (a new process) per attempt and a provider that fails every fifth request; the rows have the shape SP1 asserts; a new process after completion asks the provider for the top of the spine only; an awaiting_spine status row round-trips through `proof_finality_status`.
- `pr/rb11-prod-shape-check.sh` gains SP1 (spine rows: 32-byte hash, item `spine/n<1..40>`, every row, a window cut at a leg block too, ends at block = 39 mod 40, bytes an RLP list of 400 to 2048 bytes per header) and SP2 (awaiting_spine status rows carry numeric have <= need and a next_attempt_at, only on Sepolia). Run read-only on the live host at 19:25Z, before the merge with Train 2 and when the two checks were still named C8 and C9: 91 checks, 86 PASS, 5 WARN (D3 D4 D6 as before, the two new ones "none yet"), 0 FAIL; SP2 reports the 11 `finality_build_timeout` rows that the fix replaces. Against a database filled by the Go test: SP1 PASS (54 rows), SP2 PASS (1 row).
- Table growth: a row is about 26 to 27 KB (40 headers of 645 to 674 bytes). At 12 s blocks the finalized chain adds at most 180 aligned rows a day (4.7 to 4.9 MB), shared by all legs, plus at most one cut row (the lowest window of a leg, 27 KB at most) per distinct leg start; the one-time backlog of the 11 live legs is 116 aligned rows and at most 11 cut rows (3.1 to 3.4 MB). The ceiling is bounded by the chain, about 1.8 GB a year, and the insert-only trigger (migration 00028) forbids pruning, so the table grows at that rate for as long as Sepolia legs are finalized.

## Deploy note

Non-consensus: no govRoot input, no consensus gate, no signature rule, no format a verifier reads. No migration (`proof_finality_capture` accepts chain 11155111 and the item names). No new required environment variable. Validators can be restarted one at a time. `CERTEN_FINALITY_BUILD_TIMEOUT_SECONDS` stays as it is; raising it was never the fix. Owner configuration note OQ-R11-7: a keyed Sepolia RPC (`ETHEREUM_SEPOLIA_RPC_URL`) makes the spine faster but is no longer required.

## Findings (not fixed here)

- Seven validators on one host share one provider address and one database; each fetches a chunk the others have not stored yet. They find each other's rows when they read the store before each fetch, and fetch it once per process, but nothing coordinates two validators fetching the same chunk in the same second (the cost is a duplicate request, never a wrong row).
- A chunk the process fetched but could not write (store error) stays in the process cache and is not written again while it is cached; durability returns when it is fetched again after eviction or restart (`TestAStoreThatFailsPausesTheSpineAndLosesNoProgress`). The cache is first in, first out (a read does not refresh an entry), which is enough because an evicted chunk comes back from the store.
- Real cadence after the deploy (from the review): the status row's `next_attempt_at` is a not-before. The upgrader's schedules are per pass (Interval 60 s after the previous pass ends, a pass lasts until its slowest leg), so an attempt per leg is about 5 to 9 minutes apart, not 2 s.
- `finality_spine_row_invalid` is `ClassFailure` in the retry table because Train 2's `TestRB12F17TheEnvironmentClassIsExactlyTheProcessAndStoreStates` pins the environment class to two states. Since a wrong row is now a miss that the leg goes past, the state is a record (log and counter) and no longer a stop, so the class only matters to a row the build cannot get past, and there is none.
- `cmd/finalityethsepoliarecord` builds with a Prover that now stops after the default 150 s of new fetching; a recording of a very long spine reports the progress state and is run again.
