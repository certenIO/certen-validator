# RB11 staged finality: alert thresholds

All series are exported on the validator's `/metrics`; the same state (without history) is the `finality` member of
`/health/detailed`. None of these alerts concerns settlement, attestation or write-back: the finality upgrader and the capture
loops sit beside them. A level a leg lacks is a named state, never a failure of the leg. Thresholds are starting values for the
first week in shadow; tune them from the measured per-chain etas of V2_SPEC_S7 8.1.

| Metric | Condition | Severity | Why |
|---|---|---|---|
| `certen_finality_upgrader_enabled` | `== 0` on any validator (or differs between validators) | warning, page if the fleet was meant to be on | The default is ON; an off switch is the named state `finality_upgrader_disabled` (log line and `certen_finality_upgrader_disabled_total{chain="0"}`). A validator that stops appending leaves its legs at `included` for as long as no other validator appends. |
| `certen_finality_chain_enabled{chain}` | `== 0` for a chain that has live legs | warning | A per-chain switch (`CERTEN_FINALITY_CHAIN_<id>_ENABLED=false`) or missing provider configuration; the reason is in `/health/detailed` (`disabled_reason`) and in `certen_finality_upgrader_disabled_total{chain,env}`. |
| `increase(certen_finality_upgrader_disabled_total[1h])` | `> 0` after a deploy that was not meant to switch anything off | warning | One increment per announced named state: the setting that caused it is the `env` label. |
| `certen_finality_capture_lag_blocks{chain,capturer}` | `> 60` for 10 minutes | warning; `> 90` for 5 minutes: critical | Tenderly serves `eth_getProof` only about 8 blocks below the head and the other public providers at most 100. A capture loop further behind than the window records `l1_proof_window_unavailable` / `batcher_state_unavailable` and the missed block can then only be redone from an archive or paid provider (`CERTEN_FINALITY_ARCHIVE_URLS`). |
| `time() - certen_finality_last_append_unixtime{chain}` | `> 2 x` the slowest level's eta of the chain while `certen_finality_legs{level!="finalized"}` is non-zero | warning | An upgrader that is on but appends nothing. Etas: Sepolia and Base `l1_posted` about 20 min, Arbitrum `finalized` about 110 min, Base `finalized` about 5.3 days, Adiri up to 6 h + 5 min. Do not alert for Base `finalized` on this metric alone. |
| `time() - certen_finality_last_pass_unixtime` | `> 5 x` the pass interval (default 60 s; use 10 min) | critical | The upgrader's pass loop stopped advancing (a hung store is bounded by `StoreTimeout`, so this means the process lost the loop). |
| `increase(certen_finality_capturer_restarts_total{chain,capturer}[1h])` | `> 5` | warning | A capture loop that keeps failing or panicking; the supervisor restarts it with a bounded backoff, the failing state is in the log. |
| `increase(certen_finality_status_total{state=~"l1_proof_window_unavailable\|batcher_state_unavailable\|l1_blob_unavailable\|finality_lc_unavailable"}[30m])` | `> 0` and rising for 30 minutes | warning | The builder could not establish an input it needs (a missed provider window, a beacon blob API without the blobs, no light-client endpoint). Each is a named state in `proof_finality_status`; the leg keeps the level it has. OD3 (own beacon node) and OD4 (archive provider) remove the usual causes. |
| `rate(certen_finality_provider_throttled_total{provider_host}[1h])` | `> 30` per hour for one host | warning | HTTP 429 backoffs. The limiter slows down by itself; a sustained rate means the per-provider rate limit is above what the provider allows (the Arbitrum public RPC answers 429 to batches of 100 requests; batches are capped at 40). The label is a host name only. |
| `increase(certen_finality_capture_refused_total{chain,code}[1h])` | `> 0` | warning | A capture refused by a named state, for example `finality_evidence_too_large` when a block's rows exceed `CERTEN_FINALITY_MAX_CAPTURE_BYTES_PER_LEG`. Nothing is truncated; the block is not captured and the state names why. |
| `rate(certen_finality_capture_bytes_total{chain}[1h])` | above 4 MiB per captured leg on average, or growing faster than the chain's observed traffic | info | The capture tables are insert-only and nothing is deleted: this is the disk growth rate to budget (Base about 1.1 MB per leg with blobs). |
| `increase(certen_finality_chain_broken_total{chain}[5m])` | `> 0` | page | A stored addendum chain failed verification against the leg binding recomputed from the verified Settlement. Should never be non-zero; nothing is appended to that leg until it is looked at. |
| `increase(certen_finality_build_failures_total{code="finality_verifier_failed"}[1h])` | `> 0` | warning | A builder produced evidence its own registered Kind refuses: a bug or a provider answer that parses but does not verify; nothing was stored. |
| `increase(certen_finality_status_write_failures_total{chain}[15m])` | `> 3` | info | The status table is not authoritative; the next pass writes it again. A burst means the database is slow, which also bounds the upgrader. |
